## Context

`OuterMetaComponent%write_restart` and `%read_restart` already branch on `currentPhase` (`GENERIC_INTERNAL_WRITE_RESTART` / `GENERIC_INTERNAL_READ_RESTART`) with empty bodies (see proposal.md - Why). The existing netCDF path reaches `import`/`export`/`internal` `ESMF_State`s via `this%get_user_gc_driver()%get_states()` (a `MultiState`), and both `write_restart.F90` and `initialize_read_restart.F90` independently call `MAPL_StateGet(state, bundle, rc)` (`superstructure/state/StateGet.F90`) to flatten a state's Field/FieldBundle items into one `ESMF_FieldBundle` before handing it to `RestartHandler%write`/`read`. `FieldClone` (`infrastructure/esmf/FieldPointerUtilities.F90`) already performs a structural (metadata + independent allocation, no data) clone of a single `ESMF_Field`. No `FieldBundleClone` or bundle-level data-only copy exists; `FieldBundleCopy` (`infrastructure/field_bundle/FieldBundleCopy.F90`) copies data between two *already-allocated, same-shape* bundles and asserts field counts/names match.

## Goals / Non-Goals

**Goals:**

- Implement the two empty internal-phase branches so they perform a real in-memory checkpoint write/read, reusing the existing `MAPL_StateGet(state, bundle, rc)` bundle-flattening logic rather than duplicating it.
- Add exactly one new small piece of general infrastructure (`FieldBundleClone`) needed to deep-clone a flattened bundle; keep it generic (not restart-specific) so it lives in `infrastructure/field_bundle/`, consistent with `FieldBundleCopy`/`FieldBundleCreate`.
- Store at most one snapshot per component instance; a new write replaces any prior one (per user decision - no keyed/multi-snapshot history).
- Gate which of import/export/internal participate using the *existing* `checkpoint_controls` (write) and `restart_controls` (read) flags already used by the netCDF path, so in-memory and file-based checkpointing share one configuration surface.

**Non-Goals:**

- Serializing the in-memory checkpoint to disk, transferring it across PETs/processes, or persisting it beyond the lifetime of the `OuterMetaComponent` instance.
- Changing `RestartHandler`, netCDF file formats, filenames, or the existing `checkpoint_controls`/`restart_controls` types.
- Supporting multiple named/keyed in-memory snapshots (explicitly deferred by user decision).
- Deep-copying nested `ESMF_State`s or `ESMF_FieldBundle`s that themselves contain nested states (the existing `MAPL_StateGet` flattening already has this limitation for the netCDF path; in-memory path inherits the same scope).
- Recursing into child components: only the single `OuterMetaComponent` instance whose `write_restart`/`read_restart` is invoked is checkpointed, matching how the internal branches already skip `recurse_write_restart_`/child recursion (see `write_restart.F90`). Checkpointing a subtree (needed for predictor/corrector algorithms) requires recursion and is deferred to a follow-up change (explicit user decision).
- Providing any production call site that actually triggers `GENERIC_INTERNAL_WRITE_RESTART`/`GENERIC_INTERNAL_READ_RESTART`. `GenericGridComp.F90` registers these phases for `ESMF_METHOD_WRITERESTART`/`READRESTART` on every generic component (added by the prior `internal-checkpoint` change), but nothing in the codebase - not `GriddedComponentDriver`, not `Cap` - ever calls `ESMF_GridCompWriteRestart`/`ReadRestart` with these phases. This change implements what the branches *do* when invoked; it does not add a caller. The only exerciser after this change is the new pFUnit tests (Task 6), which call `ESMF_GridCompWriteRestart`/`ReadRestart` directly. A real driver-level trigger (e.g. a `GriddedComponentDriver`/`Cap` API for "checkpoint this subtree to memory now" / "restore now") is separate future work, to be designed alongside subtree recursion above (explicit user decision).

## Decisions

- **New `OuterMetaComponent` type component `memory_checkpoint : type(ESMF_State)`, holding three nested states.** Per the user's explicit design direction, add one `ESMF_State` type component to `OuterMetaComponent` (declared alongside the existing `private` fields in `OuterMetaComponent.F90`), and inside it nest three `ESMF_State`s under fixed names `"import"`, `"export"`, `"internal"` via `ESMF_StateAdd`, mirroring the `MultiState` naming convention (`superstructure/component/MultiState.F90`). Alternative considered: three separate `ESMF_State` type components (`memory_checkpoint_import`, `..._export`, `..._internal`) instead of one nested state - rejected because the user specified a single `memory_checkpoint` component with 3 nested states, and nesting also lets future work retrieve/traverse the whole checkpoint as one ESMF object (e.g. for size/attribute inspection) rather than three independent handles.
- **Lazy creation, not eager allocation in the constructor.** `new_outer_meta` (`OuterMetaComponent/new_outer_meta.F90`) stays untouched; `memory_checkpoint` and its three nested states are created on first use inside the write path (first call to the internal write branch), mirroring how `MultiState`'s constructor lazily creates states only when not supplied (`MultiState.F90:41-46`). A private logical component `has_memory_checkpoint` (or equivalently checking `ESMF_StateIsCreated`) tracks whether a snapshot has ever been written, so read-before-any-write can fail clearly (per spec's "Read with no prior write" scenario) instead of operating on an uncreated state.
- **Shared helper for building the restart-eligible field bundle.** Extract the field-selection logic currently duplicated across `write_restart.F90` (`MAPL_StateGet` + `MAPL_FieldBundleFilter(bundle, predicate_incomplete_)`) and `initialize_read_restart.F90`/`RestartHandler%read` (`predicate_skip_restart_`) into one helper (e.g. `RestartHandler`-private or a new small module function) that both the existing netCDF `RestartHandler%write`/`read` and the new in-memory write/read call. This satisfies the proposal's refactor goal and keeps in-memory and netCDF checkpoint semantics for "which fields count as restart data" from silently diverging. Alternative considered: let the in-memory path re-implement its own field filtering - rejected, this is exactly the duplication the proposal calls out.
- **In-memory write = per-field `FieldClone` over the flattened bundle (new `FieldBundleClone`).** Write branch, for each enabled state (import/export/internal, per `checkpoint_controls`): build its flattened bundle via the shared helper, then call new `FieldBundleClone(bundle_in, bundle_out, rc)` to produce an independently-allocated bundle whose fields are `FieldClone`s of `bundle_in`'s fields (structure/metadata only, fresh memory - `FieldClone` never copies data, so no accidental aliasing of live model memory into the checkpoint). Store `bundle_out`'s fields into the corresponding nested state under `memory_checkpoint` (replacing any prior contents for that state - old fields/bundle destroyed first). Alternative considered: use `MAPL_FieldBundleCopy` for the deep copy - rejected, that procedure requires a pre-existing, same-shaped destination bundle; the checkpoint has no such bundle yet on write, so clone-then-copy is redundant work when `FieldClone` already handles allocation.
- **`FieldBundleClone` is new infrastructure, built from existing `FieldClone` + `FieldBundleCreate`.** Signature: `FieldBundleClone(bundle_in, bundle_out, rc)`, in a new `infrastructure/field_bundle/FieldBundleClone.F90` (module `mapl_FieldBundleClone_mod`), exported as `MAPL_FieldBundleClone` through `mapl_field_bundle_api` (`infrastructure/field_bundle/API.F90`), following the exact pattern already used for `FieldBundleCopy`. Implementation: create output bundle via `FieldBundleCreate`, iterate `ESMF_FieldBundleGet(..., fieldList=...)` on the input, `FieldClone` each field, add clones to the output bundle.
- **In-memory read = data-only copy, not a fresh clone.** Read branch, for each enabled state (per `restart_controls`): fetch the corresponding nested state's already-flattened bundle from `memory_checkpoint`, fetch the live state's current bundle via the same shared helper, and call existing `MAPL_FieldBundleCopy` (`infrastructure/field_bundle/FieldBundleCopy.F90`) to copy data values field-by-field into the live fields - satisfying the spec's "live fields remain the same field objects" scenario. This mirrors `FieldClone`'s own data/structure split: clone (write) allocates, copy (read) only moves data. Alternative considered: destroy and replace live fields with clones from the checkpoint on read - rejected, this would break any existing pointers/aliases downstream components hold into the live import/export/internal states, and contradicts the spec requirement that read is "data-only."
- **Missing-snapshot-on-read is a hard failure (`_FAIL`/`_ASSERT`), not a silent no-op.** Matches the spec's explicit scenario; implemented via the `has_memory_checkpoint` flag (or `ESMF_StateIsCreated` check) at the top of the read branch, checked per-state so a partially-written checkpoint (e.g. only `checkpoint_controls%get_import()` was true on the prior write) fails only for the states actually requested by `restart_controls` on read.
- **Reuse existing `checkpoint_controls` / `restart_controls` flags verbatim.** Per user decision, no new "in-memory enabled" flag is introduced; the internal write/read branches gate on `this%component_spec%misc%checkpoint_controls%get_import/export/internal()` and `...restart_controls%get_import/export/internal()` exactly as the netCDF branches already do below them in the same procedures. This keeps one configuration surface for "does this state get checkpointed/restarted," whether via file or in memory.

## Risks / Trade-offs

- [`ESMF_State` type components with no destructor are added to `OuterMetaComponent`, which itself has no `final`/destroy procedure today (only `free_outer_meta` frees the *inner* meta/user gridcomp)] -> Follow existing project convention (no explicit `OuterMetaComponent` destroy exists for its other ESMF handles either, e.g. `self_gridcomp`, `hconfig`); do not introduce new lifecycle machinery in this change. Note the gap in tasks.md as a follow-up rather than solving it here.
- [Lazy creation means `memory_checkpoint`'s nested states may never be created if write is never called, and a read call must distinguish "not yet created" from "created but empty"] -> Explicit `has_memory_checkpoint` logical (or equivalent per-substate check) checked before any `ESMF_StateGet` on `memory_checkpoint`, avoiding operating on an invalid ESMF handle.
- [Extracting a shared field-selection helper touches both existing netCDF call sites (`write_restart.F90`, `initialize_read_restart.F90`) as well as the new in-memory paths] -> Keep the refactor behavior-preserving (same predicates, same `MAPL_StateGet` call), covered by existing restart pFUnit tests plus new in-memory round-trip tests; no change to on-disk file output expected.
- [`FieldBundleClone` duplicates some structure-walking already done by `FieldBundleCreate`'s `create_bundle_from_field_list` and by `state_get_bundle`] -> Keep `FieldBundleClone` minimal (bundle-in -> bundle-out via per-field `FieldClone`); do not attempt to unify with `state_get_bundle`'s state-to-bundle flattening, which solves a different problem (State -> Bundle, not Bundle -> Bundle).
- [Storing full independent copies of import/export/internal fields in memory increases peak memory footprint for the lifetime of the component] -> Out of scope to optimize in this change (no compression/subsetting); note as an accepted trade-off given the "single latest snapshot" design decision, which already bounds worst case to one extra copy.

## Migration Plan

Additive change: new type component, new branches in two existing (currently empty) procedures, one new small infrastructure procedure, and a non-behavioral refactor of existing field-selection logic into a shared helper. No existing public API signatures change. Build and run existing generic/restart pFUnit suites plus new in-memory checkpoint round-trip tests with `module load nag-stack`. Rollback consists of reverting the internal branches to empty bodies, removing `memory_checkpoint` and `FieldBundleClone`, and reverting the shared-helper extraction - no persisted data or file formats are affected, so no data migration is needed either direction.
